# 0007 Error Handling and Logging

## Context and Problem Statement

MCP clients must be able to distinguish errors from useful partial results. At
the same time the operator needs diagnostic information without logging the
API key or unnecessary user data.

## Considered Options

1. Return errors as normal answer text.
2. Separate MCP errors with fixed codes from structured partial results, log
   JSON to stdout.
3. Build a dedicated central logging stack for the first release.

## Decision

**Option 2**.

### Tool errors

An error is a tool result with `isError: true` and exactly one text content
holding this JSON:

```json
{"error": {"code": "string", "message": "string", "request_id": "string"}}
```

| Code | When | Message (fixed) |
| --- | --- | --- |
| `invalid_input` | input violates the tool contract | `Invalid input: <field> <rule>.` |
| `url_not_allowed` | URL fails the input check from ADR 0008 | `URL is not allowed.` |
| `url_unreachable` | Gemini could not retrieve the URL | `URL could not be retrieved.` |
| `url_unsafe` | Gemini reports the URL as unsafe | `URL was rejected as unsafe.` |
| `upstream_unavailable` | 429, transient 5xx or timeout after all retries | `Search backend is temporarily unavailable.` |
| `upstream_error` | any other Gemini error | `Search backend returned an error.` |
| `internal_error` | unexpected error in the server | `Internal error.` |

For `invalid_input`, `<field>` and `<rule>` name only the field and the violated
contract rule, never input values, Pydantic or exception texts. On client
cancellation no result is produced. A successful search with incomplete sources
is not an error.

### Logging

Every tool call produces exactly one JSON line on stdout:

| Field | Content |
| --- | --- |
| `ts` | ISO 8601 UTC |
| `level` | `info` or `error` |
| `event` | `tool_call` |
| `request_id` | UUID4 generated by the server |
| `tool` | `search` or `analyze_url` |
| `status` | `ok`, `error` or `cancelled` |
| `error_code` | code from the table or `null` |
| `duration_ms` | total duration |
| `model` | Gemini model used |
| `input_tokens`, `output_tokens` | from API usage metadata, otherwise `null` |
| `query` | only when `LOG_QUERIES` is enabled (ADR 0010), otherwise absent |

Technical error details go into an additional line with `event:
"error_detail"` and the same `request_id`. Never logged: API key,
authorization header, bearer token, secrets and web content.

## Consequences

- Good: Agents can recognize failed calls and re-plan.
- Good: Container and Kubernetes logging can collect JSON directly.
- Bad: Troubleshooting requires access to operator logs.
- Bad: Enabled query logging is relevant for data protection.

## Open

Log retention and access control belong to the cluster infrastructure, not the
server.
